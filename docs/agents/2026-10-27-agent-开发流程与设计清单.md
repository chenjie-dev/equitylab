# Agent 开发流程与设计清单

> 创建日：2026-10-27。人读 SSOT：编排层 / 工具面 / harness / eval 改动前对照。  
> 执行流程 skill：`equitylab-agent-dev`；落地：`equitylab-dev`；收尾：`equitylab-dod`。  
> 摘要来自公开材料（OpenAI Harness Engineering / Agent Evals、Anthropic Managed Agents 权限、OWASP MCP、DenisSergeevitch agents-best-practices、Google Developers harness 行为套件等），**非产品背书**；本仓落地以 registry + 硬闸 + smoke/DoD 为准。

## 1. 本仓流程（优化后的最小环）

改 Agent 能力时按序推进；每步有完成判据。细节与命令落点见 skill。

```text
Spec → 工具进注册表 → 确定性算数 ⊥ 模型 → 权限闸
  → Trace → Eval（轨迹/契约/冒烟）→ 改进飞轮 → DoD
```

| 步 | 做什么 | 完成判据 |
|---|---|---|
| Spec | 任务、工具、成功/失败、禁止动作、轮次/超时/成本预算 | 可勾选验收条；无「更智能」类空目标 |
| 注册表 | `apps/orchestrator` `TOOL_REGISTRY`：name + description + schema + run | 无散落直打下游 |
| 算数 ⊥ 规划 | IC/回测/行情在 research 确定性引擎；模型只规划与解释 | 响应带 `mode`/`source`/`demo`；缺数不编造 |
| 权限闸 | always / ask / never；服务端硬闸优先于 prompt | 超时、轮次、零上游、不下真实单可测 |
| Trace | `X-Trace-Id` + tool start/ok/fail | 失败能定位工具与参数 |
| Eval | 轨迹断言 → 契约字段 → 可复跑 smoke | 仅 `health=200` 不算完成 |
| 飞轮 | 失败 trace → 回归 case → 改 harness → 重跑 | 不只靠「再试一次 prompt」 |
| DoD | skill **equitylab-dod** | `已做 / 未做 / 已知风险 / 复验命令` |

**复杂度要赚回来**：加 planner / 多 Agent / 重试 / 投票 / 子 Agent 前，先对比「单环 + 现有工具」基线；无评测增益则不加。

## 2. 市面 Agent 项目提示：设计前应考虑的问题

下列问题在业界 harness / eval / MCP 安全材料中反复出现。本仓改工具或循环时，**至少过一遍**；勾选可记入 DoD 或 PR 说明。

### 2.1 测什么（单元在测）

- [ ] **测的是部署中的 harness**（指令 + 工具 + 权限 + 停止规则 + 上下文），不是裸模型？
- [ ] 换模型 / 换 harness 能否**分开**对比，避免把模型能力误当成脚手架效果？
- [ ] 新增复杂度（多步规划、重试、子 Agent）是否相对**简单单环基线**有可测收益？

### 2.2 工具设计

- [ ] 每个工具是否**单一职责**、文档写清到「人类工程师只看 description+schema 就能用」？
- [ ] 工具之间是否**尽量少重叠**（避免模型随机挑同义工具）？
- [ ] 参数 schema 是否严格（必填、枚举、范围）；错误是否**结构化返回**而非散文堆栈？
- [ ] 缺数 / 超时 / 空结果时，工具是否返回可观测失败，而不是让模型「猜数补全」？
- [ ] 是否只暴露任务所需最小工具集（最小权限面）？

### 2.3 轨迹与正确性

- [ ] Eval 是否断言：**该调的工具 / 禁止的工具 / 参数关键字段**，而不只看最终自然语言？
- [ ] 复杂任务是否避免锁死唯一工具顺序，而锁**不变量 + 最终业务状态**（或契约 JSON）？
- [ ] 答案是否要求** grounded**：结论须能追溯到工具观察；无证据时是否鼓励弃权/澄清，而非自信幻觉？
- [ ] 是否惩罚「看起来完成但未调用必要读工具 / 忽略工具失败」的假成功？

### 2.4 安全与权限

- [ ] 危险副作用（写库、外呼、资金相关）是否 **ask / never**，且闸在**执行层**而非仅 system prompt？
- [ ] 用户输入与工具返回是否当**不可信数据**（防间接注入驱动特权工具）？
- [ ] 若接 MCP：描述/schema 是否审过；外部 MCP 与特权内部工具是否隔离；写操作是否需人确认？
- [ ] 本仓专属：**读路径零上游**、**不接真实券商下单**、密钥不进仓、demo 指标不冒充生产？

### 2.5 停止、成本与延迟

- [ ] 轮次上限、单工具超时、总预算是否有硬闸（本仓立项：≤5 轮、单工具 ≤30s）？
- [ ] Eval 是否同时看质量、安全、**成本与延迟**，避免「高分但不可部署」？
- [ ] 重试是否有上限，且对幂等/非幂等工具区分策略？

### 2.6 可观测与回归

- [ ] 一次失败能否用 Trace 回答：调了谁、参数、观察、停在哪？
- [ ] 生产/联调失败是否会**固化成回归 case**（脚本或测试），进仓可复跑？
- [ ] 评测是否可重复（固定 fixtures、记录模型/指令/工具包版本）？
- [ ] 是否防止 reward hacking：Agent **不能改自己的 grader**；冒烟脚本与断言不可被业务路径改写？

### 2.7 套件形状（建议覆盖）

业界建议的均衡套件（本仓按能力裁剪，不要求一次全做）：

| 类型 | 要验证的行为 |
|---|---|
| Happy path | 干净完成，正确工具 + 契约字段 |
| Near miss | 缺参时澄清或拒绝，不瞎编 |
| Tool-use | 选对工具、参数合法、观察进回答 |
| Permission | 危险调用被拦或需审批 |
| Failure | 超时、空结果、畸形工具输出时降级 |
| Adversarial | 注入/越权尝试不能绕过 never 闸 |
| False-success | 无证据不得宣称「已算出 IC/夏普」 |

### 2.8 EquityLab 数据面（Agent 侧连带）

- [ ] Agent 展示/解释的标的 ⊆ 采集就绪集，或标明「仅目录、暂无报价」？
- [ ] 因子/回测数字来自冷库或标明 `demo`；`source`/`data_source` 诚实？
- [ ] 产品路由仍是 `cn-equity` 等产品名，而非 `sina`/`adata`/`ashare`？
